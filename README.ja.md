# Rashid — Rosetta 亡き後も Intel アプリを動かす

[English README](README.md)

## 目標

**Rosetta が macOS から削除された後も、Apple Silicon 上で Intel (x86_64) の
macOS アプリを起動できること。**

達成基準:

1. Rosetta が存在しない macOS で、x86_64 の Mach-O を rashid が起動できる
2. Apple のプライベート entitlement / SIP 保護領域 / カーネルの翻訳経路に
   一切依存しない (= 通常ユーザ権限で動く)
3. 再配布可能 — Apple のコードを同梱しない

Rosetta 本体は流用できない。実測で確認済み (「Rosetta を流用できない理由」
参照): 入口 (カーネルの exec 判定) と出口 (libRosettaRuntime) の両方が
Apple 側にあり、真ん中の翻訳器だけ取り出しても繋がらない。
だから翻訳レイヤは自作する。

Wine が Win32 API を再実装するのとは違い、**macOS のフレームワークは
arm64 版が既に存在する**ため、API の再実装は不要。必要なのは
CPU 命令の翻訳と、ネイティブ dylib を呼ぶための ABI 変換 (thunk) だけ。

## アーカイブの役割

`rosetta-archive-<version>/` は目標に対して**ビルド時の依存**であり、
実行時の依存ではない。thunk 方式では実行時に呼ぶのはネイティブ arm64 の
フレームワークなので、x86_64 の dylib は成果物に同梱しない (達成基準 3)。

| 退避物 | 用途 | 時点 |
|---|---|---|
| x86_64 dyld 共有キャッシュ | thunk シグネチャの生成元 (型エンコーディング) | ビルド時 |
| MacOSX.sdk | x86_64 テストバイナリのコンパイル | ビルド時 |
| Rosetta ランタイム | 翻訳品質の参照・検証 | 開発時のみ |
| AOT キャッシュ | 同上 | 開発時のみ |

例外は将来のフォールバック経路。thunk を書いていないマイナーな
PrivateFramework については、その x86_64 版を丸ごと翻訳して動かす方が
安上がりになる場合がある。その経路を採るなら共有キャッシュは実行時依存に
変わり、達成基準 3 と衝突するので、ユーザが自分の環境から用意する形になる。

## 現状

**Rosetta 無しで動くことが実証された。** 開発機を macOS 27 へ上げたところ
Rosetta が外れ、一時的に OS が x86_64 バイナリの実行を拒否する状態になった。
その同じマシンで rashid は動いた。

```
$ ./objcclass.x86
bad CPU type in executable

$ rashid objcclass.x86
hits=5      describe=clicks=5   version=1.0
isa=Counter responds=1          byname=Counter
```

アプリが自分で定義した Objective-C クラスであり、そのメソッドは
インタプリタで走り、メッセージはネイティブ arm64 の Foundation へ届いた。

その後 macOS がオンデマンドで Rosetta を再インストールした（27 ではまだ
提供される）ので、このマシンは再び x86_64 を実行できる。しかし窓は実在し、
結果も実在した。カバレッジはまだ全く足りない（ロードマップ参照）。

### 動くもの

動くもの:

- x86_64 Mach-O のロード (thin / fat、LC_MAIN / LC_UNIXTHREAD の両方)
- 共有アドレス空間と領域ごとの権限追跡。暴走したゲストポインタは
  翻訳器を巻き込まず、その場で正確に報告される
- 整数命令サブセット (キャリー付き `adc`/`sbb` を含む ALU、flags、jcc、
  call/ret、mul/div、movzx/movsx、cmovcc、setcc、shld/shrd、pushfq/popfq)
- **TLS**。macOS x86_64 はスレッドの TSD を `%gs` に置き、machine-dependent
  syscall `0x3000003` で設定する。`pthread_getspecific` は
  `movq %gs:(,%rdi,8), %rax` の1命令 (`%fs` は macOS では未使用)
- **SSE**。コンパイラ生成コードが実行する SIMD 命令の 99.3% をカバー (下記)
- ゲストのメモリ管理: `mmap` (匿名)、`mprotect`、`munmap`
- **動的ロード**。`LC_DYLD_CHAINED_FIXUPS` を辿り、イメージを rebase し、
  同一プロセスに既にロードされているネイティブ arm64 フレームワークに対して
  全 import を解決する
- **C 関数の thunk**。翻訳されたコードがネイティブ arm64 の libSystem を
  呼び、正しい結果を受け取る。可変長引数を含む
- **Objective-C**。セレクタをネイティブランタイムに登録し、クラスと定数文字列を
  実オブジェクトに bind し、メッセージ送信をマシン上の arm64 Foundation で走らせる
- **ゲストコードへのコールバック**。ネイティブフレームワークが翻訳された
  コードを呼び戻せる — `qsort` のコンパレータ、メソッド実装
- **アプリ自身が定義するクラス**。インスタンス変数、クラスメソッド、
  `super` 呼び出しを含む
- クラス判定付きの syscall: `read` / `write` / `close` / `exit` /
  `thread_fast_set_cthread_self`

動かないもの: AppKit と GUI 全般、カテゴリ、プロトコル、ブロック、
AVX、x87、シグナル、スレッド、ファイル実体を伴う `mmap`。

Objective-C バイナリが最後まで動き、実機と同一の出力を出す。

```
len=23              range=6,9           double=2.50
prefix=1            count=3 first=x     dict=v
format=built/7      NSLog reached with hello objective-c world (23)
```

### Objective-C は予想より簡単で、予想外に難しかった

`objc_msgSend` には特別扱いが一切要らなかった。可変長引数に見えるが違う。
コンパイラは各呼び出し地点の本当のシグネチャを知っていて通常の呼び出しを
出すので、System V と AAPCS64 のレジスタ割り当てが一致し、汎用 thunk が
そのまま通る。

必要だったのは、本来 dyld がランタイムに伝える内容のほう。イメージ内の
セレクタ参照はそのイメージ自身の文字列を指しており、`objc_msgSend` は
セレクタを文字列ではなくポインタで比較するため、ロード時に全て
ネイティブランタイムへ登録し直す。クラス参照と定数文字列は、データ
シンボルの直接 bind で既に解決している。

本当に作業が要ったのは3点。いずれも動かして誤りを目撃して見つけた:

- 16バイト構造体は片方が `rax:rdx`、もう片方が `x0:x1` で返る。`x0` しか
  拾っていなかったので `[s rangeOfString:]` が「もっともらしい位置と
  ゴミの長さ」を返した
- `NSLog` の書式は C 文字列ではなく **NSString**。読むにはオブジェクトに
  バイト列を尋ねる必要がある — 相手はネイティブなので普通のメッセージ送信
- `stringWithFormat:` など一部の ObjC メソッドは可変長引数を取る。メソッドの
  型エンコーディングは宣言された引数しか記述しないので可変長性は metadata
  から判別できず、セレクタを一覧で引くしかない

### アプリが定義するクラス

クラスは公開ランタイム API — allocate / add methods / register — で構築し、
実装は全て trampoline に差し替える。実装は x86_64 コードなので、ランタイムを
直接そこへ入らせるわけにいかない。インスタンス変数も同様に宣言し、ランタイムが
決めたオフセットをイメージ側へ書き戻す。コンパイル済みの ivar アクセスは
そこを読むため。

残るのは同一性の問題。イメージは自分のクラスをアドレスで参照する。clang は
`_OBJC_CLASS_$_Foo` への直接の `leaq` を出すので、差し替えるべき間接参照が
ない。素直な解 — 完成したクラスオブジェクトをイメージ側へ複写する — は
**通用しない。libobjc は arm64e であり、ポインタをアドレス依存で署名している**。
別アドレスへ移したクラスオブジェクトはもう有効ではなく、ランタイムがそう言う。

そこでイメージ側の構造体はハンドルとして扱う。それがどの実クラスを表すかを
rashid が覚えておき、ゲストが境界を越えて渡すときに本物へ差し替える。
同一性が観測されうるのはそこだけである。

```
hits=5          describe=clicks=5     version=1.0
isa=Counter     responds=1            byname=Counter
```

`RASHID_OBJC_DEBUG=1` で何を見つけ何を登録したかが出る。

### 逆方向の呼び出し

thunk は翻訳されたコードがフレームワークを呼ぶための仕組み。アプリには逆も
要る。`qsort` はコンパレータを呼び、フレームワークはデリゲートを呼び、
Objective-C ランタイムはメソッド実装を呼ぶ。いずれも arm64 の呼び出しとして
到着し、x86_64 のインタプリタに行き着かねばならない。

rashid はアセンブルされた trampoline の並びからアドレスを配る。各 trampoline
は自分の番号を読んで共通のディスパッチャへ飛び、ディスパッチャが引数
レジスタと呼び出し元のスタックを捕らえ、インタプリタの状態を退避し、ゲスト
関数を走らせ、結果を AAPCS64 の期待する場所に戻す。実行時生成ではなく
アセンブル済みなので、`MAP_JIT` も W^X の手当ても要らない。

ネイティブ関数のどの引数がコールバックかはシグネチャなしには分からないので、
`qsort`・`bsearch`・`atexit` など一般的なものを列挙している。可変長引数と
同じ欠落であり、同じ解決策を待っている。

### ABI 境界を越える

整数の規約はほぼ一致している。System V の `rdi, rsi, rdx, rcx, r8, r9` が
AAPCS64 の `x0..x5` になり、浮動小数点は片方が `xmm0-7`、もう片方が
`v0-v7`。小さなアセンブリの呼び出しゲートが、選んだレジスタとスタック状態で
ネイティブ関数に入り、`x0` と `d0` の両方を回収する。どちらの返り値レジスタが
意味を持つかは、rashid が知らないかもしれないシグネチャ次第だからである。

import されたシンボルがコードかデータかで bind 方法が変わる。関数は stub を
経由させねばならない。直接 bind するとゲストが arm64 命令を x86 として
実行しようとするため。データ — Objective-C のクラスオブジェクト、
CoreFoundation の定数 — は呼ばれず参照されるだけなので、ネイティブアドレスに
直接 bind する。名前から推測するのではなく、シンボルを自身のイメージ内で
引いて、含まれる**セクション**が命令を持つかで判定する。セグメントでは
足りない。`__TEXT` は実行可能だが読み取り専用データも抱えており、
全クラスが指す `__objc_empty_cache` は `(__TEXT,__const)` にある。

可変長引数は本当の作業を要する。**macOS arm64 は可変長引数を全てスタックで
渡す**が、System V は最初の数個をレジスタで渡す。転送するには引数の個数と
型を知る必要があり、書式付き入出力の一群についてはそれが書式文字列から
分かるので、rashid は書式を解析して呼び出しを組み直す。それ以外の可変長
関数は既知の欠落である。シグネチャなしではレジスタで渡してしまい誤動作する。

### 最初の1本まであとどれくらいか

Cocoa の hello world (`NSString`、`NSLog`、autorelease pool) が import する
シンボルは **8個**:

```
_NSLog                                Foundation
_OBJC_CLASS_$_NSString                Foundation
_objc_autoreleasePoolPop              libobjc
_objc_autoreleasePoolPush             libobjc
_objc_msgSend                         libobjc
_objc_release                         libobjc
_objc_retainAutoreleasedReturnValue   libobjc
___CFConstantStringClassReference     CoreFoundation
```

これが最初のマイルストーンの実際の大きさ。先に数えた C 関数 32,444 個は
最終的な表面積であって入場料ではない。アプリが触るのはその小さな、そして
大部分が共通の部分集合にすぎない。8個のうち6個は Objective-C ランタイムの
入口であり、`objc_msgSend` を**通った先**は手書きではなく生成された thunk
が担う。

```
make             # ビルド
make test        # freestanding ゲスト 2 本 + fault 封じ込め 3 種
./rashid -l FILE    # ロードだけして構造をダンプ
./rashid -m FILE    # ゲストアドレス空間マップを表示
./rashid -t FILE    # 全命令トレース
```

### アドレス空間

**ゲストは rashid とアドレス空間を共有する。ゲストポインタはホストポインタ
そのものである。**

これは選択ではなく強制である。翻訳されたコードがネイティブ arm64 の
フレームワークを呼ぶときポインタを渡し、ネイティブ側はゲストが後で読む
メモリにポインタを書き込む — 構造体の中、ObjC オブジェクトの中、
コールバックに渡されるバッファの中に。境界で変換するにはポインタのグラフを
全て辿ることになり非現実的なので、両者はアドレスの意味について合意して
いなければならない。Wine も box64 も同じ理由でアドレス空間を共有している。

帰結として、イメージは必ずしもリンクされたアドレスに置けない。
x86_64 イメージは `0x100000000` を望むが、そこは arm64 実行ファイル
すなわち rashid 自身が置かれる場所であり、リンカは動かしてくれない
(arm64 では `-no_pie` も `-image_base` も無視され、`-pagezero_size` は
4GB で頭打ち)。したがって PIE イメージは slide し、非 PIE イメージは
黙って誤配置せず明確なメッセージで拒否する。2011 年頃以降にビルドされた
x86_64 macOS アプリは全て PIE である。

rashid が追跡するのは、ゲストに渡した領域とその権限。全アクセスをそれと
照合するので、暴走したポインタは「どこか後で落ちる」ではなくその場の
正確な報告になる。サンドボックスではなくデバッグ支援であり、thunk が
入れば緩める必要がある — その時点でゲストは正当にネイティブメモリへ
到達するようになるため。

権限は領域ごとに記録し `mprotect` ではなくソフトウェアで強制する。
ホストページは 16KB、x86_64 イメージの配置は 4KB 境界なので、1つの
ホストページが権限の異なるセグメントにまたがることが常態化している。
権限を外側に丸めると隣のセグメントが黙って書き込み不可になる。

## テスト

ゲストは freestanding な x86_64 バイナリで、計算結果を終了コードとして返す。
`make test` はその値を2通りで検証する — 実機の x86_64 から記録した値と、
x86_64 を実行できるマシンであれば同じバイナリを実機で走らせた結果と。

このフォールバックはもう仮定ではない。開発機が macOS 27 へ上がって Rosetta を
失ったとき、比較は全て `tests/expected/` の記録値へ退避してテストは緑のままだった。
その後 Rosetta が戻り、実機比較は記録値と一致した。記録値の検証としては
これ以上のものはない。

```
== behaviour (exit status must match real x86_64) ==
  hello    rashid=0    native=0    ok
  arith    rashid=55   native=55   ok
  tls      rashid=15   native=15   ok
  ripimm   rashid=255  native=255  ok
  sse      rashid=21   native=21   ok
  vm       rashid=9    native=9    ok
```

実機比較のほうが強い。自分の思い込みではなく本物の CPU と突き合わせるため。
そして macOS 28 で失われる。だから今のうちに期待値を記録しておく。

既に3回効果があった。RIP 相対変位が即値の分だけずれるバグ、`0F C2`
(`cmpeqsd` — C の `==` はこれになる) の未実装、`adc`/`sbb` の未実装。
どれも「近くのそれらしい値」を返すため、実機比較なしでは気づきにくい。

## 速度

`make bench`。M1 で、同じバイナリを Rosetta 経由で走らせたものとの比較。

```
startup: native 11.8ms, rashid 6.1ms

work       guest instr    native    rashid   ratio  compute  M instr/s
int         42,000,052     17.3m    543.2m     31x      98x       78.2
mem         60,000,059     17.4m    972.6m     56x     171x       62.1
flt         78,000,070     39.4m   1093.4m     28x      39x       71.7
hash        90,001,360     24.6m   1396.6m     57x     109x       64.7
thunk       28,000,082     33.3m    452.4m     14x      21x       62.8
```

インタプリタは毎秒 6000〜8000万ゲスト命令。ゲストが実際に実行するコードでは
Rosetta の 20〜170 倍遅い。switch ディスパッチのインタプリタとしては普通の
数字であり、これを詰めるのが JIT の仕事。内訳も示唆的で、浮動小数点が 39 倍で
済むのは1命令あたりの仕事量が大きいため、thunk 主体が 21 倍で済むのは rashid が
ほとんど解釈していない（どちらもネイティブ arm64 の libSystem で処理される）ため。

反復回数が大きいのは Rosetta が速いから。1/10 にすると native 側はほぼ全部が
プロセス起動時間になり、そこから起動時間を引いた compute 比は実行ごとに
100〜500倍の間を動いた。差を取る列は、引く量より測る量がずっと大きくないと
意味を持たない。

アプリ全体では話が変わる。アプリの時間の大半は自分のコードではないから。

```
app            guest instr    native    rashid   ratio
native                  70     10.7m      6.1m    0.6x
objc                   187     14.8m     10.8m    0.7x
objcclass              282     14.5m      9.4m    0.6x
```

rashid の起動は半分の時間で済む。翻訳するものが無いから — フレームワークは
既に arm64 である。したがって損益分岐点があり、それは数十万ゲスト命令のあたり。

```
  iterations   guest instr    native    rashid   ratio
           0            49     11.3m      6.5m    0.6x
      10,000        70,052     13.1m      7.8m    0.6x
     100,000       700,052     11.6m     16.1m    1.4x
   1,000,000     7,000,052     12.3m     97.1m    7.9x
```

それ以下なら起動だけで rashid が勝つ。それ以上では解釈が支配し Rosetta が離す。
短命なツールは既に競合できる。計算するものは下のブロックコンパイラ次第で、
この表はそれを使っていない。

記録しておくべき否定的結果がひとつ。`mem` が 171 倍と最悪で、アクセスごとの
権限チェックが領域リストを走査するせいに見えた。直前にヒットした領域を
キャッシュしてみたところ、**わずかに遅くなった**。リストは短く、そこに時間は
無い。この筋ではない。

### ブロックコンパイラ

`rashid -j` でブロックをコンパイル。`-J` は各ブロックをインタプリタで
再実行して照合してから信用する。

```
work      native   interp      jit  jit/interp  jit vs native
int        13.2m   190.4m    23.1m       8.22x           1.8x
mem        13.1m   334.2m    26.9m      12.41x           2.1x
flt        21.2m   376.3m    39.2m       9.60x           1.9x
hash       16.0m   476.6m    47.0m      10.15x           2.9x
thunk      16.3m   114.1m    46.7m       2.45x           2.9x
```

8/32/64ビットの整数演算を、レジスタ・即値・メモリ（ベース、スケール付き
インデックス、ディスプレースメント、RIP 相対）の各オペランドでコンパイルし、
`lea`、`inc`/`dec`、`push`/`pop`、シフト、`imul`、`movzx`/`movsx`、`setcc`
を扱い、`jcc`・`jmp`・`call`・`ret` とその間接形でブロックを終える。
ゲストの状態は `rsd_cpu` に置いたままで、まだ見ていないメモリと頻度の低いフラグは
インタプリタ自身のルーチンを呼ぶので、命令の**意味**の大部分は両エンジンで一つの定義を
共有する。例外は下に書いた。

`hash` はシフト・乗算・バイトをコンパイラに教えた変更のときに足した。
実際の整数コードの大半はこの形であり、最初のコンパイラはこれを一つも
コンパイルできず、インタプリタと同じ 387ms で走っていた。

`RASHID_JIT_PROFILE=1` を付けると、実行のどれだけがコンパイルされたかと、
インタプリタが結局何を実行させられたかをオペコード別に報告する。上の実装順は
そのリストで決めた。`int`・`mem`・`flt`・`hash` は実行命令の 100%、`thunk` は
86% がコンパイル済み。残りはインポートスタブで、これは設計上インタプリタの仕事。

#### 8ビットオペランドの代償

C では現れようのない x86 の規則が2つあり、コンパイラもテストも偶然には
つまずかない:

- **バイト書き込みは残りを保つ。** `al` への書き込みは `rax` の残り7バイトを
  そのまま残す。`eax` への書き込みが上位4バイトを消すのとは逆である。
  コンパイル済みコードは `str` ではなく `strb` で書く
- **`ah`・`ch`・`dh`・`bh` はレジスタ4〜7ではない。** REX プレフィックスが
  無いとき、この番号は `rax`・`rcx`・`rdx`・`rbx` のビット 8〜15 を指す。
  REX が付くと — 全ビットが0の `0x40` であっても — `rsp`・`rbp`・`rsi`・`rdi`
  の下位バイトになる。コンパイラは「中身の無いプレフィックスを見た」ことを
  覚えていなければならない

バイトの読み出しにマスクは一切要らない。そう見えないので書いておく: 加算・減算・
ビット演算は情報を下位へ運ばないし、フラグのヘルパは渡されたものを切り詰めるので、
全幅で演算した結果の下位8ビットが既に答えになっている。取り出しが要るのは
`ah` 形式の読み出しだけ。

#### シフトが桁上げを落としていた

シフトをコンパイルするには両エンジンでシフトの定義を一つにする必要があり、
書き下ろしてみると**インタプリタ**がシフトのフラグを `and` と同じルーチンで
設定していた — 毎回 CF と OF を落としていた。x86 では CF は最後に押し出された
ビットである。シフトしてから桁上げを見るコード、つまり多倍長演算や
`__builtin_*` の桁上げ連鎖や多くのハッシュ関数は、ゼロを読んでいた。
両エンジンとも CF をきちんと計算し、OF はハードウェアと同じに計算する。
（マニュアルが未定義とする分 — AF は常に、OF はカウントが1でないとき — は
テスト側でマスクする。約束されていない挙動を固定しないため。）

シフト量ゼロは何も変えない。フラグすら変えない。そしてこれは誰も気づかない形で
壊しやすい: 最初の実行で唯一取り逃した変異が、カウント0でもシフトを実行する
というもので、2命令後にフラグが上書きされるためテストに見えなかった。
今はテストがそれを読む。

#### 時間の行き先: フラグ

次はゲストレジスタをホストレジスタに置くつもりだった。先に測ったら計画が変わった。
`sample` はコンパイル済みコードを跨いでスタックをたどれないので、取り除いて測った:
`int` のループで、フラグが一度も読まれない2命令からフラグ計算ルーチンを外すと
125ms が 76ms になった。呼び出し1回が約4ns で、ループは1周に4回呼んでいた。
時間の大半はフラグであり、ゲストレジスタのメモリへのロード・ストアではなかった。

そこで2つの変更をした。それぞれ単独で測っている:

```
              before   flags only     flags
              (calls)   when read   in line
int           120.4m       89.1m     57.5m
mem           221.5m      119.5m    118.0m
hash          273.5m      166.6m    152.8m
```

（各600万反復。上の表より大きいのはそのため。）

- **読まれるフラグだけ。** ブロックは出力を始める前に最後までデコードし、
  後ろから走査する: 各命令が書くフラグのうち、後の命令が上書きされる前に読むものは
  どれか。たいていは無い — add の後には `cmp` が来る — ので、そのときはフラグの
  コードを省く。ブロックの終わりでは全てが生きている。次のブロックかインタプリタが
  何を読んでもよいから。解析は命令が**確実に**書くフラグを知っている必要がある:
  `inc`/`dec` は CF を残し、ここでの論理演算は AF を残し、`cl` によるシフトは
  `cl` が0なら何も書かないので、何も上書きしない
- **残りはインラインで。** なお必要なものは呼び出しではなく arm64 自身のフラグから
  計算する: 演算を正しい幅の `cmn`・`cmp`・`tst` として繰り返し、CF・ZF・SF・OF を
  NZCV から読む（借りは arm64 のキャリーが**クリア**のとき）。arm64 に無い PF と AF は、
  シフト付き `eor` 3回と `a ^ b ^ r` から作る。`jcc` と `setcc` の条件はフラグ語から
  直接読む

2つ目の変更は、これまでコンパイラが守ってきたもの — 命令の意味をインタプリタと
一つの定義で共有すること — を手放す。これらのフラグには定義が2つになった。基準は
今もインタプリタの方で、-J がブロックごとに両者を比較し、新しい8つの変異 — 読み手を
無視する解析、CF を書くとされた `inc`、フラグを書くとされた `cl` シフト、arm64 の
キャリーとして扱われた借り、反転したパリティ、別のビットからのニブルキャリー、
64ビットで取った32ビットのフラグ、ZF 抜きの `le` — が、それに気づくことを確かめる。
バイト演算は引き続きインタプリタのルーチンを使う。arm64 に8ビットのフラグ設定形が無いため。

8つのうち1つは初回に取り逃しと報告されたが、誤りはテストではなく変異の側にあった:
`cl` シフトには即値が無いので、書き換えた条件もやはり0になり、何も変わっていなかった。
スクリプトが確かめる「変異が適用された」はテキストの比較でしかない。

#### メモリをインラインで

`mem` はフラグの変更では動かなかった。残っていたのが、ロード・ストアのたびに、
ゲストがそのアドレスに触れてよいかを決める権限検査付きでインタプリタを呼ぶコスト
だったから。その検査を、できるときはインラインで行うようにした: 直近のコンパイル済み
ロードと、直近のコンパイル済みストアが成功した領域を覚えておき、その内側へのアクセスは
減算1回・符号なし比較1回と `ldr`/`str` そのものになる。それ以外 — 新しい領域、
領域の境界、そもそもゲストのメモリでないアドレス — は今まで通りインタプリタの
ルーチンへ行き、そこで完全な検査をし、必要ならフォールトし、次のために領域を覚える。
`mmap`・`mprotect`・`munmap` はどれも、覚えたものを全て忘れさせる。

```
              flags     memory
              in line   in line
mem           104.6m     66.0m
hash          153.6m    129.1m
thunk         192.1m    169.2m
```

覚える領域は種類ごとに1つではなく2つ。1つだと `thunk` が 8% **遅く**なった:
ループはバッファに1バイト書いてから `strlen` を呼び、呼び出しはスタックに戻り番地を
書くので、2つのストアが2つの領域に交互に当たり、毎回外れ、しかも外れると領域を
2回探すことになっていた。ループ内でメモリに一切触れない `flt` は、ずっと 2.6% 遅い
ままだった。ブロックの配置を揃えても変わらなかったので、ループのコードの置き場所の
せいではない。原因はまだ分かっていない。下の次の変更で、原因がありそうな経路は
ループから外れる。

テストが届かなければならないのは境界である。`tests/jitmem.c` は、覚えた領域を1バイト
だけはみ出す8バイトを読む — その領域が2つのうち新しい方のときと、古い方のときに1回
ずつ — のと、読み取り専用にした後の領域への書き込みをする。どれもインタプリタと全く
同じにフォールトしなければならない。このテストの初版は、謳っていることを何も検査して
いなかった: ヘルパ関数が戻る前に `pop rbp` でスタックを読むので、境界を読む時点では
いつもスタックが新しい方の領域になっていた。今はアクセス列をそれぞれ1つの `asm` 文に
している。

書いている途中で、シフトをコンパイルし始めた時からあったバグも見つかった。メモリ
オペランドの `cl` シフトは、オペランドを読む呼び出しを跨いでカウントを `x5` に置いて
いたが、`x5` は呼び出しで壊れうる。インタプリタのロードルーチンがたまたま `x5` を
使わなかったから動いていた。

そして `-J` の穴も見つかった。本来より広いストアは、どのログ項目も指さないバイトを
変える。記録した書き込みを巻き戻してもそこは変わったままで、インタプリタは同じ変わった
バイトを見るので、両エンジンは一致してしまう。32ビットのインラインストアに8バイト
書かせる変異は、これが理由で取り逃していた。今は記録する書き込みごとに周囲16バイトを、
書き込み前と、各エンジンが残した状態とで保持し、それも比較する:

```
rashid: jit and interpreter disagree at 0x1041ad000
  bytes around the write to 0x1041af000 differ:
    jit    c3c3c3c3a5a5a5a5210000002c000000
    interp c3c3c3c316000000210000002c000000
```

それでもこの変異が検出されたのは、`tests/jitint.c` に、上位半分に値のあるレジスタから、
隣が0でないメモリへのストアを足してからだった。それまでは、余分に書かれたバイトが
いつも元々そこにあった値と同じだった。

#### この先を伸ばすもの

ディスパッチャに戻らずにブロックからブロックへ移ること（`int` と `flt` に残っている
のはこれ）、ゲストレジスタのホストレジスタ化、16ビットオペランドと `0x66`
プレフィックス、そして SSE の長い裾。それぞれ別の変更にする。どれも独自の変異を要るから。

スカラ SSE もコンパイルする: 移動、四則演算、`min`/`max`、`sqrt`、比較述語8種、
`comis`、ビット演算、型変換。それ以前は `flt` がインタプリタより**遅かった**
(0.83倍) — 整数部分はコンパイルされたが SSE 命令ごとにブロックが切れ、
出入りの往復が節約分を上回っていた。今はインタプリタの9倍、Rosetta の3倍以内。
`-j` はまだデフォルトではない。

#### x86 の浮動小数点が arm64 と違うところ

NaN・符号付きゼロ・無限大・範囲外の値で作ったテストを実機と比較したら、
**インタプリタ**の誤りが2つ見つかった — そしてインタプリタに忠実に一致していた
コンパイラも同じく誤っていた:

- **生成される NaN の符号。** 通常の入力から NaN を作る演算 (`0/0`、`sqrt(-1)`、
  `inf-inf`) で、x86 SSE は符号ビットの立った NaN (`0xFFF8000000000000`) を返し、
  arm64 は符号ビットの無い NaN を返す。入力が既に NaN なら x86 は第1オペランドの
  それを quiet 化して返す。両エンジンとも共有ルーチンで x86 に従うようにした。
  コンパイル済みコードの負担は、結果が実際に NaN でない限り比較1回と
  成立しない分岐1回だけ
- **収まらない変換。** NaN や範囲外の値の `cvttsd2si` は x86 の「整数不定値」
  `0x80000000` / `0x8000000000000000` になる。arm64 の C キャストは飽和し NaN を
  0 にするので、`(int)3e9` が 3000000000 の下位32ビットになっていた

外れた疑いも一つ記録しておく。もっともらしく見えたので: 単精度除算を倍精度で
計算して float に丸めると2回丸めることになり、単精度で直接割った結果と違いうる。
ここでは違わない。2つの float の商は、単精度の丸め境界にちょうど乗る以外に
2⁻⁵³ 以内へ近づけない。ランダムな2億組も全て一致した。

#### 検査器を検査する

一度も失敗しない検査器は何も証明しないので、`make jit-mutations` は
コンパイラを36通りにわざと壊す — インデックスのスケールを1つずらす、
RIP 相対の基準を誤る、分岐を逆にする、32ビット加算を64ビットでやる、
`rsp` を動かさない push、結果を書き戻す `cmp`、NaN で逆の値を返す `min`、
`lt` になった `le` 述語、arm64 の符号のままの生成 NaN、64ビットとして変換される
32ビット整数、被演算子が逆の `andnot`、別のレジスタの `sqrt`、レジスタを消す
バイト書き込み、`al` として読み書きされる `ah`、`movzx` として広げる `movsx`、
マスクしないシフト量、カウント0でも実行するシフト、別のレジスタからカウントを
取るシフト、64ビットでやる32ビット乗算、反転した `setcc`、上のフラグの変異8つ、
そしてインラインメモリの6つ — 境界を含むものとした領域検査（2つのエントリそれぞれ）、
`mprotect` 後も残る領域、記録されないインラインストア、64ビットで行う32ビットの
インラインロードとストア — そして `-J` がその全てを捕まえることを要求する。

ここに至るまでに見つかったもの。どれも「テストが通った」が証拠にならなかった例:

- **メモリも比較に含める必要があった。** `add [mem], 1` のブロックを、
  既に書き換わったメモリの上で再実行しても何も検査できない。書き込みを
  記録し、再実行前に巻き戻し、比較するようにした。スケールの変異はこれ
  なしでは見えない — レジスタは全て一致し、書き込み先だけが違った
- **テストスイートがコンパイラを使っていなかった。** 分岐を逆にしても
  `tests/arith` は通った — JIT されたブロックが、成立する `jcc` で
  一度も終わっていなかった。`tests/jit.c` はそのためにあり、全変異を
  捕まえて初めて採用した
- **結果が古かった。** HFS+ は更新時刻を秒単位で記録するので、1秒以内に
  「編集→make」すると古いバイナリが残り、make は最新だと思い込む。
  「検出」と出た変異の一つは、実は変異していないバイナリで走っていた。
  スクリプトは毎回バイナリを消してからビルドする
- **コンパイラがインタプリタのバグを暴いた。** RIP 相対の変異は不一致では
  なく rashid のクラッシュになった。4バイト早く読んだ GOT エントリが
  非正規ポインタになり、`access_ok` の範囲検査が比較の前に
  `上限 - アドレス` を計算していたためラップした。ユーザ空間より上を指す
  暴走ポインタは、フォールトではなくホストのクラッシュになっていた。
  修正し fault テストを追加。rashid はホストがクラッシュした際に、
  原因となったゲスト命令を報告するようにもなった
- **XMM レジスタを比較していなかった。** 再実行の比較は汎用レジスタ・フラグ・
  メモリだけだった。NaN 修正の初版はヘルパ引数を他のヘルパと同じく `x1` から
  詰めていたが、そのヘルパは cpu を取らないので、迷子のポインタを結果として
  読んでいた。XMM を比較に加えた途端に見つかり、レジスタ名まで特定できた
- **16バイト書き込みが記録を通っていなかった。** `le` を `lt` にすると誤った
  マスクが `movapd` でメモリへ書かれ、それを持つレジスタはブロック終了前に
  上書きされる。記録していたのは8バイト以下の書き込みだけだったので、比較対象の
  どこにも差が現れなかった。今は全ての書き込みが記録を通る
- **テスト自身のチェックサムに死角があった。** `(h ^ v) * K` で混ぜると、最上位
  ビットの差はずっと最上位ビットに留まり、偶数個あると打ち消し合う。倍精度 NaN
  の符号の誤りを8回繰り返すのはまさにその形で、実際に1件隠していた。混合関数は
  上位ビットを下にも落とすようにした

## 既知の設計課題

**非 PIE イメージは動かない**
rashid 自身が `0x100000000` に置かれ、x86_64 イメージの希望ベースと衝突する。
リンカでの回避は不可能 (arm64 では `-no_pie` も `-image_base` も無視され、
`-pagezero_size` は 4GB で頭打ち)。PIE なら slide できるので実害はほぼ無い —
2011 年頃以降の x86_64 macOS アプリは全て PIE。非 PIE は明確に拒否する。

**ページサイズ**
x86_64 Mach-O は 4KB 境界、Apple Silicon は 16KB ページ。セグメントを
個別に file-map できないため匿名マップへ copy-in し、権限は領域ごとに
記録してソフトウェアで強制する (`mprotect` は使わない)。1つのホストページが
権限の異なるセグメントにまたがるのが常態なので、丸めると壊れる。
JIT では全アクセス検査ができないため別の答えが要る。

**TSO (最大の壁)**
x86 は強いメモリ順序、ARM は弱い順序。M1 は TSO モードを
ハードウェアで持つが Apple は Rosetta 専用にしか有効化しないため、
第三者は全メモリアクセスを `ldar`/`stlr` にするしかない。
マルチスレッドアプリで大きな性能ペナルティになる。

**W^X**
JIT には `MAP_JIT` + `pthread_jit_write_protect_np()` +
`com.apple.security.cs.allow-jit` entitlement + Hardened Runtime が必要。
RW/RX はスレッド単位で切り替わるので、翻訳スレッドの設計に影響する。

## Rosetta を流用できない理由 (実測)

macOS 26.6.2 で確認:

| | 実測結果 |
|---|---|
| 入口 | x86_64 の exec 判定はカーネル内。`sysctl.proc_translated` が返す |
| entitlement | `oahd` は `com.apple.private.oahd` 等を要求。署名は "macOS Software Signing"。AMFI がカーネルで検証するため自己署名不可 |
| 設置場所 | `/usr/libexec/rosetta/`、`/System/Library/LaunchDaemons/`、`/var/db/oah` (listing すら Operation not permitted) — すべて SIP 配下 |
| ランタイム | `libRosettaRuntime` は dylib ではなく `MH_EXECUTE`。エクスポートは 2 個のみ。dlopen して翻訳 API を呼ぶことはできない |

流用できたもの: `dsc_extractor.bundle` のみ (キャッシュを個別 Mach-O に展開できる)。
`translate_tool` は単体では出力を出さず、仮に出せても AOT 成果物は
libRosettaRuntime が読む private 形式なので、実行側なしでは動かない。

いずれにせよ Rashid は Rosetta を使わない。上は「近道が無い」ことの記録であって、
Apple バイナリの改変を勧めるものではない。

  アプリ)。AppKit を再実装する必要があるため長年 GUI アプリがほぼ動かない。
  Rashid がその再実装を必要としない理由の対照例として有用
- **[rozetka2](https://github.com/XS-Corp/rozetka2)** — 最も近い兄弟プロジェクト。
  同じく clean-room の x86_64→arm64 translator、MIT。MIT のコードは
  そのまま取り込める。逆方向は Apache-2.0 の条項が付いて回る
